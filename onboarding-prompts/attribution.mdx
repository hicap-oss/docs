Use this prompt for a complete attribution pass after your Hicap client is configured. The agent inventories workflows, assesses the six starter dimensions, adds source-backed tags, tests outgoing requests, and reports coverage and gaps.

This prompt uses the existing Hicap client and preserves routing, models and provider options. If the client is missing, start with [client setup](/onboarding-prompts/configure-client).

## How the prompt works

Attribution answers: **which workflow does each request belong to, and what proves it?** The agent follows four stages and leaves evidence you can review at each one.

<Steps>
  <Step title="Inspect: find the client and its callers">
    Identify existing Hicap routes and map their workflows, current tags, and service defaults. Inventory other provider paths separately.

    **You get:** an attribution coverage map. If no Hicap client exists, stop tagging work and use the client setup prompt first.
  </Step>
  <Step title="Decide: ground each label in evidence">
    Assess Env, Feature, Operation, System, Agent, and Domain using the code and approved application conventions. Distinguish observed values from proposed meanings.

    **You get:** each value's source and scope, with missing values classified as a bug, unresolved configuration, or not applicable. Do not invent labels to fill a chart.
  </Step>
  <Step title="Change: attach context where it belongs">
    Preserve reviewed tags, set service defaults in configuration, and attach feature, operation, and role context at the caller. Carry context through retries and queues where they exist.

    **You get:** focused tagging changes on existing Hicap requests. Routing, models, credentials, and other providers remain unchanged.
  </Step>
  <Step title="Prove: match every request to its workflow">
    Capture final outgoing requests from real application paths using mocked responses. Check the expected tags for each caller; a swapped or missing expected tag must fail a test.

    **You get:** a coverage report with emitted values, test evidence, and unresolved gaps. Valid JSON alone does not prove correct attribution.
  </Step>
</Steps>

**After the code changes:** review the report and diff, then verify fresh traffic after your approved deployment. Keep source configuration, mock-tested requests, live responses, and recorded Hicap attribution as separate evidence levels. The complete prompt below defines the detailed requirements.

## Full prompt

The block below is the complete instruction for your coding agent. Review it before use, then review the agent's changes and verification report. For the overall workflow, see [Set up Hicap with a coding agent](/concepts/implement-attribution-with-an-agent).

````text wrap title="Implementation prompt"
Add or repair attribution using this application's existing Hicap client.
Inspect the existing setup, make focused tagging changes, and verify tags on
actual Hicap-bound application call paths using mocked requests. This task does
not migrate inference traffic.

1. Read repository instructions and inspect the current integration.
   Trace ALL model request transports and their callers: product routes, shared
   clients, grading/agent modes, workers, scheduled jobs, benchmarks and scripts.
   Follow retries, fallbacks and queue boundaries. Reuse existing inventories but
   verify them against current source. Exclude generated/vendor output and ordinary
   non-model traffic; list inaccessible or unresolved paths.

2. Make a compact coverage table before editing.
   For each model workflow show entrypoint -> transport, current tags, expected
   agent/feature/operation/trigger and service defaults, with source references.
   Distinguish observed values, recommendations and intentional non-applicability. Inspect
   existing role/event registries; do not limit agent discovery to a multi-agent file.
   Preserve approved application conventions rather than replacing them with an
   industry preset. Ask only for decisions that block safe implementation.

3. Repair attribution at the owning boundary.
   Reuse the existing Hicap client and a small shared helper with trusted caller
   context. Keep existing endpoint URLs, credentials, model selection, provider
   options, routing and fallback behavior unchanged. Add tags only to requests
   already routed to Hicap; do not add Hicap headers or credentials to other
   destinations. Inventory non-Hicap model paths as outside Hicap attribution
   coverage without rerouting them. If no identifiable Hicap client or route is
   configured, report the missing prerequisite and point to the client setup
   prompt; skip tagging implementation and its verification. Do not create a
   client or switch providers in this attribution task. A configured route with
   unverified or failing live model access can still be assessed with mocks;
   report the access gap and do not claim live attribution is verified.

   Service defaults belong in configuration; workflow/role values belong at
   their caller or in a reviewed registry of existing roles. Carry context through
   async work and retries. Preserve streaming and existing application behavior.
   If there are no model calls, report that; do not add AI behavior for coverage.

Shared-client acceptance case:
A retrieval workflow can reuse one model for question rewriting and answering.
Keep feature ownership stable but assign the correct operation and named role at
each step (omit a role on rewriting if none exists). Use isolated caller context
or equivalent scoped clients without changing transport, model, credentials or
provider options. Verify each step and any tool follow-up independently; shared
client defaults must not flatten different operations into one attribution value.

Hicap attribution contract:
- Use the existing Hicap client targeting https://api.hicap.ai/v1 and its existing
  server-side key / api-key authentication (commonly HICAP_API_KEY). Never expose,
  log or commit credentials. Do not change authentication or route unrelated HTTP calls.
- Each in-scope Hicap-bound request sends exactly one x-hicap-tags header:
  one JSON object with string values. Preserve reviewed existing tags and merge precedence;
  reject malformed/duplicate keys or headers and unsafe values. Keep defaults
  immutable and caller context isolated across concurrent requests.
- Reuse the application's approved naming and configuration. Assess agent,
  env, system, feature, operation and domain; preserve useful existing dimensions
  such as trigger. These are conventions, not a gateway allowlist.
  agent = the responsible AI workflow or named model-powered pipeline role;
  env = explicit deployment context (NODE_ENV alone is insufficient);
  system = stable application/service; feature = the caller's business capability;
  domain = the application's approved business context or existing convention.
  operation = the model-powered action within a feature (for example create or
  update). Keep model steps separate from business features where both exist.
- Record the provenance and intended application/environment of each proposed
  default. Do not silently reuse a value from a different app, experiment or
  earlier scenario when its applicability is unclear. Surface the conflict and
  omit the value or ask the user; honor explicit current user assignments.
- A pipeline can have named AI roles without being called "multi-agent".
  Check existing workflow definitions, prompts and execution events. Reuse real
  roles; do not invent agents from filenames, SDKs, models or arbitrary strings.
- For each missing dimension distinguish a bug, unresolved configuration and
  genuinely not applicable. Do not silently omit a known role. Do not fill gaps
  with "unknown", "default", "none" or fake values just to clear a chart.
  If non-agent calls need an explicit reporting value, propose a documented
  convention and get approval before emitting it. Never tag secrets, prompts,
  direct personal identifiers, raw URLs or high-cardinality request/session IDs.
  Preserve approved opaque organization/user references established by the
  identity prompt; do not add new identity fields in this base-attribution task.
  That narrow exception requires verified privacy, storage and reporting
  handling. Read https://docs.hicap.ai/onboarding-prompts/identity for the
  identity contract; an opaque reference can still be personal data.

4. Verify the integration, including the paths that previously lacked tags.

Verification and completion:
- Scale checks to the application's actual architecture. Do not add production
  workflows, roles or queues just to satisfy a test. Mark genuinely absent paths
  not applicable; distinguish them from present but untested paths.
- Keep mock tests fail-closed: block unexpected network calls and await all
  concurrent work and retries before removing mocks, including on failures.

- Bind every captured request to its originating application workflow using a
  distinct synthetic input or an independently observed request body. Derive
  expected feature, operation and role from that workflow's behavior/instructions,
  not from the emitted tags or the implementation's attribution registry. Check
  each request and retry individually, including concurrent calls. A set of valid
  tag combinations is insufficient: swapping two callers' tags must fail a test.
  For attribution, add a negative control and demonstrate failure: use swapping
  two callers' tags when distinguishable callers exist; for a single caller,
  corrupt or remove an expected tag. Restore correct code afterwards. Synthetic
  correlation markers stay in test inputs, never in production attribution tags.
- Invoke the actual application entrypoint where feasible. A model-factory test
  does not verify its caller. Name any mocked database/auth boundary and any
  unexercised orchestration. Separately report output quality: canned responses
  prove transport and parsing only, not useful model answers.
- Use mocked provider responses. Capture the FINAL outgoing HTTP headers and URL
  from real application functions, not just the tag builder. Assert the Hicap
  destination, a redacted api-key and expected tags for Hicap-bound requests.
  Verify that non-Hicap routes and fallback destinations remain unchanged and
  receive no Hicap key or attribution header. Do not insert an expected
  agent/feature into the test context when production does not supply it.
- Check representative Hicap workflows, alternate modes, scripts/jobs and
  fallbacks. Reconcile every Hicap-bound path with an emitted-tag assertion, a
  documented non-applicable dimension, or an untested/deferred gap. Inventory
  non-Hicap paths separately and do not claim they are attributed by Hicap.
  Exercise concurrent callers and a failed attempt followed by a successful retry
  where those behaviors exist; do not invent them for coverage.
  Test enqueue/consume context when queues exist. Run relevant existing checks.
- A valid JSON header is not proof of complete attribution. Assert the expected
  values of each applicable dimension, especially named pipeline roles. An
  "Unattributed" dashboard group can mean one missing dimension while others work.
- Separate source changes, mock-tested behavior, deployed revision and fresh
  observed traffic. Historical requests retain their old tags. For live follow-up,
  use a time window after deployment, the correct application/environment, and
  the same dimensions as the chart. Compare redacted outgoing tags with recorded
  usage; do not claim a dashboard is fixed from mocks or an old 30-day aggregate.
  Do not deploy, change dashboard rules or generate paid traffic without approval.

5. Leave a short report and clear rollout steps.
   Reuse existing .hicap report conventions. Write a new Markdown report under
   <application-root>/.hicap, preserving existing reports and human notes; default
   to tagging-report.md or a timestamped sibling if it exists. Include inspected
   revision, per-workflow Hicap and non-Hicap coverage, observed and recommended
   dimension values, before/after redacted header samples, tests and gaps.
   Update README with configuration and helper usage. In the final response show
   the report path, changes, checks, remaining missing dimensions and the exact
   fresh-traffic verification needed. Do not claim complete attribution with gaps.

Current-state report requirements:
- Lead with the current source revision and prompt revision (include dirty-state
  or content hashes), selected models, SDK/adapter, destination and overall status.
  Move superseded results into a clearly labeled history section.
- List each workflow/call site separately with evidence columns: source configured,
  outgoing request mock-verified, fresh live response verified, and recorded Hicap
  attribution verified. Use passed/failed/untested/not-applicable, with evidence.
  State the denominator before reporting coverage; aggregated dimension values
  must not hide distinct call sites or untested paths.
- For Env, Feature, Operation, System, Agent and Domain show observed/emitted values,
  source and scope, suggestions separately, and reasons for omission. Explain
  intentional aggregation, such as multiple artifact formats sharing one feature.
  A generic starter package name is a candidate system name, not an approved
  business identity. Distinguish named AI roles from harness agent_type and agent_id;
  do not duplicate equivalent role dimensions or emit instance IDs without an
  established approved convention. A named persona is source evidence, not proof
  of an approved business-role taxonomy; distinguish observed persona, proposed
  role and emitted convention. Identify unresolved semantics explicitly.
- Separate pre-existing application defects, introduced regressions, untested
  integration paths and unresolved configuration. Lead with a short customer
  summary; keep detailed evidence below it.

````
