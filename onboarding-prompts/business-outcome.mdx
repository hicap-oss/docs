---
title: 'Business-outcome discovery (experimental)'
description: 'Inspect user, business-object and outcome signals after workload attribution'
---

Use this experimental prompt after configuring Hicap routing and baseline attribution. The agent investigates application-owned identity and outcome sources, reports unsupported joins, and implements only mappings supported by source and approved policy. Review proposed changes before deployment. A mocked test does not prove a live cost or outcome join.

```text wrap title="Implementation prompt"
Use this application's existing Hicap client and baseline attribution to discover and, where supported, implement an operation-level business-outcome attribution strategy. Follow repository instructions. Do not change routing, models, credentials, provider behavior, or existing baseline dimensions. Preserve any unrelated edits. Do not send live traffic, deploy or change external systems without authorization.

## Scan

1. Record repository revision, dirty state and prompt revision. Read the baseline attribution report and independently trace actual model call sites, request transports, callers, async boundaries, fallbacks and non-Hicap paths. Do not treat a report as proof of present behavior. Enumerate each distinct system/feature/operation and caller context; same labels in different workflows remain separate. Record baseline source, request destination and evidence. If no baseline exists, report the prerequisite; do not create or reroute a client.
2. For each operation trace its business purpose, actor and tenant, business object, outcome and any existing user-feedback, lifecycle, revenue and cost sources. Search database schemas AND write/read endpoints and UI or event emitters; trace provenance and relationships. Inspect update/delete, ownership, anonymous/public cases and event timing. Classify the archetype only from evidence; do not infer ticket workflows just from a support domain tag. Inventory observations separately from recommendations. If source is missing or ambiguous, say so.

## Plan

3. Produce an operation-to-outcome matrix before editing: baseline context and caller; desired outcome; existing observable signal and authority; actor, business-object and payer references; grain, cohort/window and formula; current join; proposed strategy; status; source and evidence. Every discovered operation must appear, including supporting operations, unavailable or not-applicable outcomes and untested paths. State the denominator and missing baseline paths. Distinguish an operation contributing to a shared outcome from producing that outcome; avoid double-counting outcomes or billable attempts.
4. Treat user upvotes or an existing accepted-answer event as a possible feedback signal, not proof of objective answer correctness. Record positive, negative and absent feedback separately; define eligible population, feedback coverage and owner-approved semantics. Observe whether feedback is mutable, timestamped or deleted before proposing historical windows. Do not infer ticket closure from generated text or a successful model response. Distinguish association from causation.
5. Propose relevant dimensions/references per operation using existing business concepts: for example user_id/user_key or ticket_number when the source actually supports them. Resolve identity server-side and scope to tenant/application; never use API credentials, tokens, emails, prompts or untrusted client IDs. Pseudonyms remain linkable data. Ordinary Hicap tags are string dimensions, but high-cardinality IDs require verified platform behavior and an explicitly approved customer policy. Do not silently override the baseline prohibition on personal and high-cardinality request/session IDs. If either capability or policy is unverified, propose a supported application-owned request-to-business-object join and mark it unverified until demonstrated. Keep low-cardinality business categories separate from identity.
6. Specify exact cost source and request/attempt join, retries, partial failures, shared/unattributed cost and precision. Where paid revenue is available, distinguish actual payments/refunds from invoices or plan prices, user from payer, and direct from allocated revenue; never manufacture payment data. Flag missing identifiers, unsupported export, access, retention, source semantics, feedback or authorization. Ask for only decisions necessary to implement those pieces and proceed with independent supported work.

## Implement and validate

7. Implement only source-backed, supported and approved mapping changes through the existing Hicap client or customer-owned boundary. Preserve baseline tags, request behavior, scopes, permissions and provider separation. A missing reference or a failed optional attribution write must not turn a successful model response into an application error unless the application owner explicitly requires that behavior; leave the cost or outcome unmatched and report the failure. Do not hide attribution failures. Isolate request context across concurrent users, retries and actual queues. Do not invent auth, outcome events, billing integrations, production behavior or fake identifiers; leave unsupported pieces as clear gaps. Record chosen mappings, revisions and decisions; on rerun reconcile source and flag drift.
8. Exercise actual entrypoints where feasible using network-blocked fixtures. Independently assert each expected operation and baseline header, supported new context, correct user/object association, concurrency and retries; test existing queues and fallback paths when present. Include a negative control that swaps or corrupts caller context and demonstrate it fails, then restore it. Independently exercise outcome changes, duplicate events, missing feedback, tenant collisions and shared cost where those behaviors exist. Do not manufacture missing application behaviors for coverage. Reconcile request/attempt and cost totals and count each outcome once. Distinguish mock results, actual live responses and recorded platform/outcome data.
9. Write a new `.hicap/` report without overwriting notes. Include operation-level denominator and matrix, source evidence, observed versus proposed values, user/object dimension decisions, cost/revenue and outcome formulas, redacted examples, changes, tests and negative controls, untested paths, decisions and explicit fresh validation required. If no safe implementation is possible, say so and provide a concrete prioritized plan. Never claim complete user economics from workload tags or feedback alone.
```
