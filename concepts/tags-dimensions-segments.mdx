Dimensions are tag keys attached to each request. Segments group requests using rules across one or more dimensions.

## Definitions

- A **tag** is a `key:value` pair attached to a request.
- A **dimension** is the key part of a tag, such as `agent`, `channel`, `env`, `feature`, or `system`.
- A **dimension value** is the value assigned to that key.
- A **segment** is a named, rule-defined subset of traffic. Its clauses combine dimensions with `AND`; a clause can match any of several values for one dimension.

Tags describe a request as you send it. Dimensions are the tag keys, and segments select requests using rules over those dimensions.

<Note>
  Dimensions describe a *request*. They are separate from the provisioned **Organizations**, **Applications**, **Connections**, and **Keys** described in [Organizations, Applications, Connections & Keys](/concepts/applications-connections-keys). An application may send an approved `team` dimension; that tag is not the same thing as a provisioned Hicap team or an access control.
</Note>

## How tags are sent

Attach tags to any request with the `x-hicap-tags` header. Its value is one flat JSON object mapping dimension keys to string values. Keep values short and stable; do not include credentials, prompts, direct personal identifiers, or request/session IDs. Opaque identity references require the approved handling described below.

        "model": "gpt-5.5",
        "messages": [

    const client = new OpenAI({
      baseURL: "https://api.hicap.ai/v1",

<Note>
  The header is `x-hicap-tags` (plural), and its value is a single JSON object. Send one header per request — don't repeat the header or use comma-separated pairs.
</Note>

## Reserved and conventional dimensions

Some dimensions are best set once per service so spend can be sliced consistently across every request it makes. Dimensions like `env`, `system`, and `channel` fall into this group — set them once in your client and they ride along on everything. Per-call dimensions like `feature` or `agent` then pinpoint what a specific request was doing inside that service.

Note that you don't need a dimension for which Application a request came from — that already rolls up from the Key you called with.

This is a convention and a good practice, not an enforced API restriction: enforcement is caller-side today, so it's up to your client to apply these consistently.

## Identity dimensions

Identity context describes who initiated application work. It complements the six starter dimensions; it does not replace them or Hicap's provisioned Organization, Application, Connection, or Key.

| Context | Meaning | Source |
| --- | --- | --- |
| Customer organization, when applicable | The tenant in which the initiating user is acting | Server-validated active membership and authorization; omitted in users-only apps |
| Initiating user | The person who started the workflow, not its worker or AI agent | Trusted authenticated session |
| User tier, when applicable | That user's entitlement when the workflow began | Authoritative entitlement scoped to the user and, where applicable, the active tenant |
| Trigger type | User action, scheduled work, or system event | Existing workflow entrypoint |

Reuse approved field names. When none exist, `customer_org`, `end_user`, `user_tier`, and `trigger` are possible application conventions, not reserved fields. Keep user tier separate from organization plan, wallet balance, and model tier. Preserve the initiating snapshot through delayed jobs and retries while continuing to enforce current authorization.

Organization and tier are independently optional. A users-only app can attribute its initiating user without creating a tenant. An app without personal tiers omits `user_tier`; a shared organization plan may instead be assessed as a separate `organization_plan` business dimension. Missing or blocked context in one field does not suppress other independently permitted fields. Continue enforcing the application's actual user/resource and tenant authorization.

Ordinary descriptive tags must not contain direct personal identifiers, secrets, or arbitrary high-cardinality request/session IDs. For production emission, a narrow exception permits approved opaque organization/user references only after verifying the destination's identity handling, access scoped to the application's actual user/tenant model, retention/deletion, and reporting capability. Opaque values can still be personal data. A tag never grants access.

Custom string dimensions do not by themselves establish complete per-user reporting. Dimension pickers may expose only a capped set of recent values; verify exact filtering and reporting at the expected cardinality separately. If a required capability or identity policy is unresolved, omit new affected identifier emissions and report the gap. Anonymous or system work must not be assigned an invented user.

Explicitly approved synthetic local tests may verify applicable identity capture and serialization through real application callers with a fail-closed mock transport before production capabilities are established. Use invented test-only references, never real identifiers or their hashes. Test the production emission gate separately: a synthetic flag or test environment name must not enable live emission. Local success proves neither production permission nor destination handling.

Use the [identity attribution prompt](/onboarding-prompts/identity) to assess and implement this context.

## Segments

A segment is a named set of rules for selecting traffic. For example, a segment can select requests where `env` is `production` **and** `feature` is `support`. A clause can also match any of several exact values for the same dimension, such as `feature` being `support` or `search`.

Clauses across dimensions combine with **AND**; values within an `anyOf` clause combine with **OR**. The supported operators include matching or excluding selected values and checking whether a dimension is present or absent. Do not assume prefix matching, nested groups, or OR across different dimensions are supported.

For a missing or empty dimension, a positive value match fails and an exclusion matches. Add a presence condition when you want to exclude requests with missing values from an exclusion rule.

### Segments may overlap

Segments are **not** mutually exclusive. A request can match several segment rules at the same time.

For example, consider these two segments:

- **Production support** — requests where `env` is `production` and `feature` is `support`.
- **Support workflows** — requests where `feature` is `support`.

A production support request matches **both**. Reporting on each segment can count the same request; avoid adding overlapping segment totals as though they were disjoint.

### All traffic

The unfiltered view of everything is called **All traffic**. All traffic is not itself a segment — it's simply the starting point you see before any segment rule is applied.

### Representative segments

These are examples of the kinds of rule-defined segments teams build:

| Segment | Selects |
| --- | --- |
| Batch Workloads | Requests tagged as asynchronous or bulk processing |
| Content Supply Chain | Requests that power content generation and enrichment |
| Production Support | Requests where `env` is `production` and `feature` is `support` |
| Support Workflows | Requests where `feature` is `support` |
| Non-Production Spend | Requests where `env` is present and is not `production` |
| Unattributed Traffic | Requests that arrived without the tags you expect |
| Voice Deflection Production | Production requests serving voice deflection |

An **Unattributed** group can mean a missing value for one selected dimension even when other tags are present. A named AI pipeline role should be tagged even outside an explicit multi-agent mode; a direct non-agent call may legitimately have no agent. Distinguish missing instrumentation, intentional non-applicability, unresolved configuration, historical requests, and an ingestion or display mismatch. Do not invent placeholder agents merely to clear a chart.

After deploying a tagging change, inspect fresh traffic for the correct Application, environment, and dimensions. Compare redacted outgoing tags with recorded usage. Historical requests retain their original tags; changing a helper does not backfill them.

## Structural vs. descriptive attribution

Tags and segments give you **descriptive** attribution: it comes from what you send on the request, is chosen per call, and can be redefined after the fact by editing a segment rule. This complements the **structural** attribution described in [Organizations, Applications, Connections & Keys](/concepts/applications-connections-keys), which comes from which Key you used and is fixed by how you provisioned things. Both roll up into the same spend reporting; they answer different questions.

To add attribution to your application, see [Set up Hicap with a coding agent](/concepts/implement-attribution-with-an-agent).
